End-to-end tutorial

A production-shaped analytics pipeline that never touches a cloud account

Terraform provisions a VPC, three buckets, three BigQuery datasets, a Pub/Sub topic and a VM, then installs Airflow and dbt onto that VM's operating system, deploys the pipeline and starts it. It runs against MiniSky, a local GCP emulator, so the same HCL and dbt models reach real GCP by changing one endpoint.

00

Preflight

Four things on the host. Older Docker and Terraform are fine; MiniSky must be 1.4.1 or newer.

hostbash
$ docker version --format '{{.Server.Version}}'   # 29.2.1
$ terraform version                              # v1.16.0
$ python3 --version                              # 3.12.3
$ minisky version                                # MiniSky v1.4.1

Docker needs Hub access: the emulator lazily starts fsouza/fake-gcs-server for Storage and cloud-sdk:emulators for Pub/Sub, and the VM boots ubuntu:24.04. Pull them up front on a slow link — the Pub/Sub image is ~1 GB and its first cold start takes ~90 seconds.

Clone the repository — every path and command below is relative to the example directory.

hostbash
$ git clone https://github.com/qamarudeenm/minisky.git
$ cd minisky/examples/analytics-pipeline

The finished configuration is at examples/analytics-pipeline; the steps below build it up file by file.

Ports

MiniSky binds 8080 for the API gateway and 8081 for the dashboard. If something already holds 8081, start with --ui-port 8099; the tutorial only depends on 8080.

Terraform drives two transports: the GCP REST API for infrastructure, and docker exec for everything that has to happen inside the VM. The dotted edge is the one the emulator has to provide — without it nothing on the VM can reach the APIs.

01

Start the emulator with a real SQL engine

By default MiniSky answers BigQuery calls with an in-memory mock — enough for terraform apply to succeed, useless for a pipeline, since every query returns zero rows. One environment variable swaps in an embedded DuckDB that executes real SQL and persists to ~/.minisky/data/bigquery.duckdb.

hostbash
$ MINISKY_BQ_BACKEND=duckdb minisky start
# API gateway  → http://localhost:8080
# Dashboard    → http://localhost:8081
Verify 
$ curl -s localhost:8080/compute/v1/projects/p/global/networks | head -c 60
{"kind":"compute#networkList","items":[...
CGO

The DuckDB backend needs CGO_ENABLED=1. The published Linux release has it; the macOS and Windows builds fall back to the empty-result mock, so build from source there.

02

Point the Google provider at localhost

The stock hashicorp/google provider with per-service endpoint overrides — no plugin, no fork. MiniSky routes by URL prefix, so each service gets the path its API uses.

versions.tfhcl
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.45"
    }
  }
}
providers.tfhcl
provider "google" {
  project = var.project_id
  region  = var.region
  zone    = var.zone

  # Any well-formed bearer token is accepted. access_token avoids the
  # local ASN.1 key-parsing errors a mock credentials JSON triggers.
  access_token = "minisky-local-token"

  storage_custom_endpoint   = "${local.minisky_endpoint}/storage/v1/"
  compute_custom_endpoint   = "${local.minisky_endpoint}/compute/v1/"
  big_query_custom_endpoint = "${local.minisky_endpoint}/bigquery/v2/"
  pubsub_custom_endpoint    = "${local.minisky_endpoint}/"
}

Pin to the 5.x line: newer majors send request shapes the shims have not been validated against.

Which services are reachable

Usable prefixes: /storage/, /bigquery/, /compute/, /v1/projects/*/topics|subscriptions. A Cloud SQL shim exists but no route reaches it, so google_sql_database_instance fails. Design around what routes.

03

Firewall rules before the VM, or you lose the install

MiniSky maps a VPC onto a Docker bridge network, and turns an INGRESS allow rule into a published port by tearing down and re-provisioning every VM on that network — Docker can only fix port bindings at container-create time.

Create the VM first and the rules second, and the container is rebuilt after Airflow was installed onto it. Terraform reports success; everything you installed is gone. 

flowchart TD
  N["google_compute_network"] --> F1["firewall: airflow 8080"]
  N --> F2["firewall: trino 8090"]
  F1 --> VM["google_compute_instance
depends_on both rules"]
  F2 --> VM
  VM --> R["terraform_data.vm_ready"]
  R --> I["terraform_data.install_stack
apt · python · airflow · dbt"]
  I --> D["terraform_data.deploy_pipeline
DAGs · dbt project · env.sh"]
  D --> S["terraform_data.start_services"]

Each stage is its own node, so editing a dbt model redeploys the code without reinstalling Airflow. The depends_on into the VM is load-bearing.

network.tfhcl
# auto_create_subnetworks is true on purpose: the compute shim routes
# /global/networks and /global/firewalls but has no subnetworks handler,
# so a google_compute_subnetwork resource would 404.
resource "google_compute_network" "pipeline" {
  name                    = "${var.name_prefix}-analytics-vpc"
  auto_create_subnetworks = true
}

resource "google_compute_firewall" "airflow_ui" {
  name      = "${var.name_prefix}-allow-airflow-ui"
  network   = google_compute_network.pipeline.name
  direction = "INGRESS"

  allow {
    protocol = "tcp"
    ports    = [tostring(var.airflow_port)]
  }

  source_ranges = ["0.0.0.0/0"]
}
compute.tfhcl
  # Load-bearing. See above.
  depends_on = [
    google_compute_firewall.airflow_ui,
    google_compute_firewall.trino_ui,
  ]
Verify — after the VM exists 
$ docker port minisky-vm-analytics-orchestrator
8080/tcp -> 127.0.0.1:36781
8090/tcp -> 127.0.0.1:40501

Docker assigns host ports at create time and they change on every rebuild. Read them back with docker port rather than hardcoding.

04

Lake, warehouse and event bus

Three buckets by zone, three datasets in a medallion layout, one topic. The subtlety is ownership: Terraform declares the raw tables and the staging and marts datasets, then stops. Tables inside staging and marts belong to dbt — two tools managing one object is how you get a permanent diff.

storage.tf · bigquery.tfhcl
resource "google_storage_bucket" "raw" {
  name          = local.buckets.raw
  location      = "US"
  force_destroy = true
}

# Seed data lands in the lake, so the DAG's first task reads from GCS
# exactly as it would against real Google Cloud Storage.
resource "google_storage_bucket_object" "seed_orders" {
  name         = "seeds/orders/raw_orders.csv"
  bucket       = google_storage_bucket.raw.name
  source       = "${path.module}/seeds/raw_orders.csv"
  content_type = "text/csv"
}

resource "google_bigquery_table" "raw_orders" {
  dataset_id          = google_bigquery_dataset.raw.dataset_id
  table_id            = "orders"
  deletion_protection = false

  schema = jsonencode([
    { name = "order_id",    type = "INT64",  mode = "REQUIRED" },
    { name = "customer_id", type = "INT64",  mode = "REQUIRED" },
    { name = "order_date",  type = "DATE",   mode = "REQUIRED" },
    { name = "unit_price",  type = "FLOAT64",mode = "REQUIRED" },
  ])
}

A table declared with a schema is materialised in DuckDB as <dataset>__<table> — the same name the SQL translator rewrites project.dataset.table to at query time, which is why SELECT * FROM retail_raw.orders resolves.

05

The VM is a container, and that shapes two choices

A google_compute_instance becomes a Docker container named minisky-vm-<instance>, booted with tail -f /dev/null. Two consequences.

The boot image is a Docker image. initialize_params.image takes a family id (ubuntu-2404-lts, debian-12) or a raw Docker reference like python:3.12-slim. Prefer 24.04 — it ships Python 3.12, which Airflow supports, so provisioning downloads no interpreter.

There is no guest agent. metadata.startup-script is stored but never executed, and with no SSH daemon remote-exec has nothing to connect to. Software arrives another way — next step.

compute.tfhcl
resource "google_compute_instance" "orchestrator" {
  name         = var.vm_name
  machine_type = "n1-standard-4"
  zone         = var.zone

  boot_disk {
    initialize_params {
      image = "ubuntu-2404-lts"
    }
  }

  network_interface {
    network = google_compute_network.pipeline.name
    access_config {}
  }

  metadata = {
    # Kept for parity with real GCE. MiniSky stores it but does not run
    # it, so the same steps are driven from provision.tf instead.
    startup-script = file("${path.module}/scripts/startup-script.sh")
  }
}
06

Installing software onto the VM from Terraform

The transport is docker exec against the container backing the instance, driven by local-exec. Terraform keeps the whole lifecycle: infrastructure, OS packages, application code, running services.

provision.tfhcl
resource "terraform_data" "install_stack" {
  triggers_replace = [
    terraform_data.vm_ready.id,
    filesha256("${path.module}/scripts/install_stack.sh"),
    local.guest_fingerprint,   # hash of every file in scripts/guest
    var.airflow_version,
    var.dbt_bigquery_version,
  ]

  provisioner "local-exec" {
    command     = "${path.module}/scripts/install_stack.sh"
    environment = local.provision_env
  }
}

The host script copies a guest installer into the container and runs it. Each stage writes a marker file, so a re-apply redoes only what is missing.

scripts/install_stack.shbash
docker exec "$VM_CONTAINER" mkdir -p /opt/pipeline/{bootstrap,cache,logs,.state}
docker cp ./guest/. "${VM_CONTAINER}:/opt/pipeline/bootstrap/"

docker exec \
  -e "MINISKY_ENDPOINT=${GUEST_ENDPOINT}" \
  -e "AIRFLOW_VERSION=${AIRFLOW_VERSION}" \
  -e "DEBIAN_FRONTEND=noninteractive" \
  "$VM_CONTAINER" bash /opt/pipeline/bootstrap/install.sh

The VM has to be able to reach the emulator

GUEST_ENDPOINT is not localhost — inside the container that is the container. Which address works depends on the setup, so probe rather than guess: on Docker Desktop the daemon runs in its own VM and only host.docker.internal resolves; on plain Docker Engine the gateway is the host.

scripts/lib.shbash
guest_endpoint() {
  local container="$1" port="${2:-8080}" candidate gw
  gw="$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.Gateway}}{{end}}' "$container")"

  for candidate in host.docker.internal "$gw" 172.17.0.1; do
    if docker exec "$container" \
         curl -sf -m 3 -o /dev/null "http://${candidate}:${port}/compute/v1/projects/probe/global/networks"; then
      printf 'http://%s:%s' "$candidate" "$port"; return 0
    fi
  done
}

Use the image's Python, and never upgrade pip in place

Ubuntu 24.04 ships Python 3.12, which Airflow 2.10 supports, so check for a usable interpreter before downloading one. Install through python -m pip: upgrading pip inside a fresh venv leaves the bin/pip console script pointing at internals the new version moved, surfacing later as an unrelated-looking ImportError: cannot import name 'open_rich_spinner'.

scripts/guest/install.shbash
SUPPORTED_PYTHONS="3.9 3.10 3.11 3.12"
system_version="$(python3 -c 'import sys; print("%d.%d" % sys.version_info[:2])')"

make_venv() {
  # Deliberately no `pip install --upgrade pip` here.
  "$SYSTEM_PYTHON" -m venv "$1"
}

venv_install() {
  local venv="$1"; shift
  "$venv/bin/python" -m pip install --quiet --retries 10 --timeout 60 "$@"
}

venv_install "$AIRFLOW_VENV" "apache-airflow==${AIRFLOW_VERSION}" --constraint "$CONSTRAINTS"
07

Making dbt authenticate against an emulator

dbt-bigquery has no endpoint setting and no anonymous auth mode: left alone it calls google.auth.default(), finds no credentials and fails. Two patches to the client library fix it without touching a dbt file — point bigquery.Client at the emulator, and return anonymous credentials.

scripts/guest/minisky_bq_shim.pypython
_ENDPOINT = os.environ.get("MINISKY_ENDPOINT")

if _ENDPOINT:
    os.environ.setdefault("BIGQUERY_EMULATOR_HOST", _ENDPOINT)

    def _install_anonymous_credentials():
        import google.auth
        from google.auth.credentials import AnonymousCredentials

        def _minisky_default(*_a, **_kw):
            return AnonymousCredentials(), _PROJECT

        google.auth.default = _minisky_default

    def _install_bigquery_endpoint():
        from google.cloud import bigquery
        _original_init = bigquery.Client.__init__

        def _patched_init(self, *args, **kwargs):
            kwargs["client_options"] = ClientOptions(api_endpoint=_ENDPOINT)
            if kwargs.get("credentials") is None:
                kwargs["credentials"] = AnonymousCredentials()
            return _original_init(self, *args, **kwargs)

        bigquery.Client.__init__ = _patched_init

Load it with a .pth file, not by naming it sitecustomize.py. Only one sitecustomize can win, and Ubuntu ships its own at /usr/lib/python3.12/sitecustomize.py, which precedes site-packages on sys.path. A shim by that name is never imported, and the only symptom is dbt failing to authenticate with no explanation.

scripts/guest/install.shbash
DBT_SITE="$(${DBT_VENV}/bin/python -c 'import site; print(site.getsitepackages()[0])')"
install -m 0644 "${PIPELINE_HOME}/bootstrap/minisky_bq_shim.py" "${DBT_SITE}/"
printf 'import minisky_bq_shim\n' > "${DBT_SITE}/zz_minisky_bq_shim.pth"

# Fail here, loudly, rather than at dbt's first query.
"${DBT_VENV}/bin/python" -c 'import sys, minisky_bq_shim; sys.exit(0 if minisky_bq_shim._ENDPOINT else 1)' \
  || { echo "shim did not pick up MINISKY_ENDPOINT" >&2; exit 1; }
Verify 
$ dbt debug --profiles-dir /opt/pipeline/dbt

All checks passed!
08

The dbt project is ordinary

That is the whole claim of this setup. The profile is a stock bigquery target with method: oauth — nothing in it mentions the emulator, because the shim handles that outside the file. Delete the shim, set real credentials, and the same project runs against BigQuery proper.

pipeline/dbt/profiles.ymlyaml
minisky_analytics:
  target: local
  outputs:
    local:
      type: bigquery
      method: oauth
      project: "{{ env_var('MINISKY_PROJECT') }}"
      dataset: "{{ env_var('BQ_DATASET_STAGING') }}"
      location: US
      threads: 1
models/marts/fct_daily_revenue.sqlsql
-- Cancelled and returned orders are excluded from revenue but still
-- counted, so the loss stays visible.
with orders as (
    select * from {{ ref('stg_orders') }}
)

select
    order_date,
    count(*) as orders_total,
    sum(case when is_lost_order then 1 else 0 end) as orders_lost,
    count(distinct customer_id) as unique_customers,
    round(sum(case when is_lost_order then 0 else net_revenue end), 2) as net_revenue
from orders
group by order_date

Sources reach the Terraform-owned raw dataset through env_var, so the single env.sh Terraform writes configures both Airflow and dbt.

09

The DAG: extract, load, transform, publish

Five stages. The only emulator-specific thing in the file is the endpoint it reads from the environment.

pipeline/dags/retail_analytics_pipeline.pypython
@task
def announce_raw_loaded(results: list[dict]) -> None:
    client = MiniSky.from_env()
    # A mapped task's collected XComs arrive as a lazy sequence, which the
    # JSON encoder cannot serialise — materialise it before it goes into
    # a message body.
    client.publish(
        PUBSUB_TOPIC,
        {"event": "raw.loaded", "tables": list(results)},
        attributes={"stage": "raw"},
    )

dbt_build = BashOperator(
    task_id="dbt_build",
    bash_command=(
        f"cd {DBT_PROJECT_DIR} && "
        f"{DBT_BIN} build --profiles-dir {DBT_PROFILES_DIR} --target local"
    ),
)

checked >> loaded >> raw_event >> dbt_build >> extract >> announce_marts_published(extract)

load_source is a dynamically mapped task, one per source object. The list() is not cosmetic — without it the task dies with TypeError: Object of type LazyXComSelectSequence is not JSON serializable.

11

Failure modes worth recognising

Each row is a real failure from building this, with the symptom you will actually see. All of them are silent or misattributed, which is what makes them expensive.

SymptomCauseFix
Airflow installed, no host port published Firewall rules created after the VM, so the container was rebuilt after provisioning depends_on the rules from the instance
dbt: 'NoneType' object has no attribute 'close' Auth shim named sitecustomize.py, shadowed by the distro's own Load it from a .pth file
ImportError: cannot import name 'open_rich_spinner' pip install --upgrade pip inside a fresh venv Call python -m pip; skip the self-upgrade
TypeError: LazyXComSelectSequence is not JSON serializable A mapped task's XComs passed straight into a JSON body list(results)
No address associated with hostname mid-install Intermittent DNS through Docker's embedded resolver Append fallback resolvers; give pip --retries 10
After restarting the emulator

Dataset and table metadata is in-memory. Restart MiniSky and the next plan sees every dataset as missing and proposes to recreate it, rebuilding the VM and reinstalling the toolchain. Keep the daemon up for a working session.

12

What this does not give you

The pipeline is real — objects on disk, SQL execution, Airflow scheduling. The emulation boundary is worth stating before anyone reads a green run as a production guarantee.

AreaReality
SQL dialectDuckDB, not BigQuery. TIMESTAMP_TRUNC and SAFE_DIVIDE are not translated — keep models to portable SQL.
IAMAny well-formed token is accepted. Policy bugs will not surface here.
Load jobsBigQuery load jobs cannot read gs:// URIs, so the DAG ingests through inserts instead.
SubnetworksNo /regions/*/subnetworks route; auto-mode VPCs only.
Cloud SQLA shim exists but no route reaches it from Terraform.
Quotas, slots, costNot modelled. Performance here says nothing about performance there.

What it does give you: an analytics stack you can destroy and rebuild in minutes, run offline, and hand to someone on their first day without an IAM request — from the same HCL, DAG and dbt models you would deploy for real.
